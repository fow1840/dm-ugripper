# HMI 连续 OFF 与状态查询无回复

## 现象与结论边界

240 的左右 HMI 在蜂鸣 OFF 后立即发送状态查询时，经常未收到回复。已停止 UGripper 服务，使用 PySerial 独占串口直接复现，因此不依赖 UGripper 的回复解析或并发串口访问。高度怀疑 HMI 固件连续命令接收/处理，但尚未抓取 MCU UART RX/TX，不能排除 USB 转串口链路或协议要求的帧间隔。

## 复现方法

- 设备：240；左夹爪 SN DAGZ122676001465，右夹爪 SN DAGY1226760096E2。本轮未记录 HMI 固件版本，工程师复测需补齐。
- 串口：`/dev/left_gripper`、`/dev/right_gripper`，115200、8N1、无流控。
- OFF：`5A 5A 0E 00 00 00 0E`。
- 状态查询：`5A 5A 04 02 00 00 06`。
- 每次写入后 flush；立即模式不额外 sleep，不代表物理线上的帧间隔严格为零。延迟模式在 OFF flush 后 sleep 25ms 再查询。
- 查询后收集 200ms 串口数据，每轮后间隔 50ms；每种模式各12轮。回复样例：`A5 A5 04 00 00 03 E8 EF`。

| 模式 | 左侧回复 | 右侧回复 |
| --- | --- | --- |
| 仅查询 | 12/12 | 12/12 |
| OFF 后立即查询 | 2/12 | 1/12 |
| OFF 后间隔25ms再查询 | 12/12 | 12/12 |

未回复轮次的接收结果为空，并非仅校验失败。原始记录：`tmp/board_results/balanced_240_20260929/hmi_probe.json`；脚本为同目录 `hmi_probe.py`（临时证据不随发行包安装）。12轮只能证明本次复现，不能证明25ms是最小或普适安全间隔。

## 影响与软件规避

OFF 保活和状态查询均每秒运行，紧邻发送容易反复无回复。上层因此误判 HMI inactive，产生硬件告警，持续异常可触发 USB restore、影响采集。

当前软件让低优先级 OFF 保活避让状态查询，两者调度时间至少错开25ms；显式蜂鸣控制仍优先，后续查询延后。没有关闭健康检查或扩大故障阈值。

## 请固件工程师检查

1. 抓 MCU RX/TX：两条命令是否完整到达；查询是否进入处理函数；回复是否发出。若 MCU 已发出回复，转查桥接/主机接收链路。
2. 检查 UART DMA/IDLE/RX ring 是否能在一次接收中解析多个完整帧，是否在处理 OFF 后清空后续字节或重启接收造成窗口丢失。
3. 检查 PWM 更新是否阻塞串口处理、长时间关中断或覆盖共享收发缓冲。上述均为待验证假设。
4. 明确协议是否规定帧间隔；若没有，应支持合法命令连续发送。若有，请给出保证值与忙状态/重试约定。

验收建议：两侧分别覆盖0/1/5/10/25ms间隔，各至少1000轮，统计有效查询与回复一一对应；同时覆盖重复OFF、ON/OFF切换、RGB与查询组合，并确认按键上报不受影响。
